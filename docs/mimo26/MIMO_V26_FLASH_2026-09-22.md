# MiMo-V2.6-Flash on two Arc Pro B70 cards (September 22, 2026)

Xiaomi released MiMo-V2.6 on September 22, 2026. The Flash checkpoint (`XiaomiMiMo/MiMo-V2.6-Flash-RL`, 309B parameters,
15B active, MIT licence) runs in Mach X from its safetensors directory, the same day:

```bash
ie serve ~/models/MiMo-V2.6-Flash-RL --ctx 65536        # OpenAI-compatible, tool calls, thinking on/off
ie-mimo26-run ~/models/MiMo-V2.6-Flash-RL --prompt "..." --n 128 --static 0 --chunk 2048
```

## What the engine runs

| part | checkpoint | on the cards |
|---|---|---|
| attention | 48 layers: 9 full-attention (4 KV heads) + 39 sliding-window (window 128, 8 KV heads), per-head sinks, K head 192 / V head 128 | an XMX (joint_matrix) prefill kernel and a split-K decode kernel written for those head sizes; the sliding-window layers keep a ring, not the context |
| dense weights | FP8 e4m3 with 128×128 block scales (qkv rows in their tensor-parallel shard order) | kept FP8 on the card: an FP8 GEMV for decode and verify rows, a per-card fp16 scratch plus oneDNN for prompt chunks |
| experts | 256 per layer, top 8, MXFP4 | three tiers: the most-used experts in VRAM (sized from free VRAM), the rest in pinned host RAM or read from NVMe, with a CPU expert path for part of the host-resident work |
| chat | the checkpoint's chat template, XML tool calls, `<think>` | the template in C++, tool calls returned as OpenAI `tool_calls`, thinking on or off per request |

Two things the checkpoint needed beyond its V4.1 relatives: the experts' SwiGLU has no clamp, and a rarely picked expert
produced a down-projection value of 150,585, past fp16's range, so expert rows stay fp32 end to end; and the
tokenizer's Qwen2 split runs over real Unicode categories (CJK punctuation, combining marks).

Serving defaults: the static expert tier fills each card's free VRAM (75 and 70 experts per layer here, 1.5 GiB
reserve), a residency ranking profiled on chat traffic decides which experts stay in VRAM, the rest is pinned host RAM
(115 GB) and 8 stream slots per layer, and prompt-lookup speculation drafts a copy of at least 12 context tokens and
verifies up to 8 rows at once (`IE_MIMO26_LOOKUP=0` turns it off).

## Measurements

Two Arc Pro B70 cards (32 GB each), 256 GB of system RAM, serving configuration unless stated. Single runs.

| workload | prefill tok/s | decode |
|---|---:|---:|
| 10 held-out Dream prompts (7 of 4.1–6.0K tokens, 3 short), 64 greedy tokens each, plain decoding | **429–472** (the 7 long) | **62.0 ms/token = 16.1 tok/s** (token-weighted; a second run 61.8) |
| 32K-token haystack, needle at 10 / 50 / 90 % | **434–438** | retrieved 3/3 |
| ~120K-token haystack, needle at 50 % (ctx 131,072) | **322–324** | 73–82 ms/token, retrieved |
| Dream (headless agent loop) against `ie serve`: write a program and its tests, run them, fix, write notes | follow-ups reused 9.0K / 10.8K / 21.2K of 10.6K / 11.0K / 22.0K prompt tokens from the live caches | **16.8 tok/s** mean (14.7–18.9); task completed in 9 min, 22 tool calls |

Quality, against upstream llama.cpp (c350a40, CPU) on a local BF16 conversion of the same checkpoint (experts
byte-identical MXFP4, dense FP8 × scale rounded to BF16):

| check | Mach X | llama.cpp |
|---|---:|---:|
| wikitext-2 perplexity, 8 × 2,048 tokens | **3.4749** | 3.4794 ± 0.077 |
| wikitext-2 perplexity, 2 × 8,192 tokens | **3.7557** | 3.7526 ± 0.084 |
| top-1 agreement / mean KL against llama.cpp's log-probs, 8,190 positions at ctx 8,192 | 97.64 % / 0.0054 | — |

Needles were also retrieved 3/3 at ~120K tokens with the tool's plain placement. Fresh processes give bit-identical
logits for the same input, and a sliding-window ring gives the same logits as a linear cache.

## How it got there

| step | effect |
|---|---|
| attention kernels for K 192 / V 128 (XMX prefill, split-K decode) | 32K prefill 34.9 → 241 tok/s, 32K decode 571–680 → 101–105 ms/token |
| router GEMM on oneDNN, sliding-window chunks on XMX, 2,048-token chunks | 32K prefill → 434–438 tok/s (serving configuration) |
| expert residency ranking from chat traffic | −16 % per decode token |
| static expert tier sized from free VRAM | −11 % per decode token |
| FP8-resident dense weights | −8 % per decode token (init 67 → 37 s, perplexity unchanged) |
| prompt-lookup speculation | −13 % per token on 256-token agent turns (70.9 → 61.4 ms, A-B-A) |

Each change was measured A-B-A on the held-out prompts before it became a default.

## Limits

- Text only: the checkpoint's vision and audio encoders are not wired. One request at a time.
- Speculative lookup verifies several rows in one forward, and a multi-row step rounds differently from one-row steps,
  so a greedy reply can take the other branch at a near-tie (every divergence found was a near-tie). `IE_MIMO26_LOOKUP=0`
  decodes one row at a time.
- On agent transcripts (long tool outputs, code, JSON) MiMo is highly sensitive to fp16- and int8-sized differences at
  particular positions: two exact fp32 computations agree to a KL of 1e-10, but two engine runs that differ only in
  chunking, the engine against llama.cpp, and the engine against the fp32 reference differ at a mean KL of 0.07–1.3 nats
  per token there, in bursts every implementation shares (0.003 on wikitext). Logit comparisons on such text measure
  the input's sensitivity, not the engine; the checks above use wikitext.
- `ie serve` replies are not bit-reproducible across a server's history: the CPU expert path's share of the work follows
  which experts the stream slots currently hold. `IE_DS41_CPU_MISS=0` turns that path off and makes them deterministic.
- MiMo-V2.6-Pro (the 574 GB checkpoint) and the bundled MTP / DFlash drafters are not qualified yet.
