# DeepSeek-V4.1-Flash — port scope (2026-09-12, no code written yet)

Weights on the 9100 PRO at `~/models/DeepSeek-V4.1-Flash`: 48 safetensors shards, **96,085 tensors,
475.2 GiB**, MIT licence. DeepSeek shipped a full reference implementation alongside them
(`inference/model.py` 1309 lines, `kernel.py` 591, `engram.py` 184, `vision.py` 119, `convert.py`, `generate.py`)
plus a 51-page tech report and the official prompt encoder. That reference is the single biggest asset here: every
format and every module can be read rather than inferred.

## 1. The finding that shrinks the job: the experts are already MXFP4

`kernel.py` names the formats outright — `FP4 = "float4_e2m1fn"`, `FE8M0 = "float8_e8m0fnu"` — and documents the
weight layout at line 493:

> *"B is stored as [N, K//2] in float4_e2m1fn_x2, logical [N, K] in fp4. The FP4 values are packed along the K
> (last) dimension."* … *"Weight: 1x32 quant on K (reduce dim), FP4 with E8M0 scale"*

The engine's existing MXFP4 expert bank (`deepseek4_experts.hpp:107`) is:

> `mx_qs[n*(K/2) + b*16 + j]` nibble bytes, `mx_e[n*(K/32) + b]` E8M0

And the shipped tensors are `w1.weight (2304, 2560) I8` with `w1.scale (2304, 160) F8_E8M0` — i.e. N = 2304,
K/2 = 2560, K/32 = 160, so K = 5120 = hidden.

> **CORRECTED 2026-09-12 (Phase 4).** This section originally read "**The layouts are identical** … No new expert
> kernel, no requantisation, no dequantisation." The plane *shapes* and the 16-code nibble *table* are indeed
> identical — but the element **order inside each 32-element block is not**. The engine's MXFP4 is gpt-oss
> interleaved (byte j carries element j in its low nibble and element j+16 in its high); V4.1 is sequential
> (byte b carries elements 2b and 2b+1). Only elements 0 and 31 of a block coincide, so feeding the shipped bytes
> to the engine's kernel returns a *permutation* of the right weights — silently, with plausible magnitudes.
> Caught by the one-hot GEMV check in Phase 4, not by any byte-level or shape-level check.
>
> The conclusion survives in weakened form: **no new expert kernel and no requantisation**, because the fix is a
> pure 16-byte shuffle applied once at upload (`ds41_expert_bank_upload`), after which every existing tuned MXFP4
> kernel runs unmodified. But "bind straight onto" was wrong, and a port that had trusted it would have produced
> fluent, confidently wrong output with no numerical alarm anywhere.

## 3. Architecture, from the tech report

552B backbone + 196B engram parameters; 8B active at prefill, 16B at decode; context to 1M.

- **Causal Encoder–Decoder (CED).** 40 layers = a 20-layer causal encoder + a 20-layer decoder. Decoder layers do
  **not** compute KV from their own hidden states; they project it from the encoder's final hidden state
  `H_{L/2}` with per-layer weights. Halves prefill. Structurally new and touches the whole forward pass.
- **CSA2 with three static modes** — Full / Reindex / Reuse — replacing V4's CSA+HCA hybrid. Main KV and indexer K
  are shared across layers; Top-K indices are reused independently of the cache sharing.
- **Hierarchical Sparse Indexer.** The decoder's first Full-mode layer builds a shared candidate pool (2048 blocks
  x 8 positions = 16,384 candidates); later Reindex layers search only within it.
- **Engram.** Sparsely-accessed conditional memory at layers 1 and 14. Huge on disk, kilobytes per token.
- **DSpark.** Speculative decoding trained separately after the backbone; three modules with their own expert pools.
- **FP4 main KV cache**, 890 bytes/token global — a quarter of V4-Flash.
- **Single-Pass mHC**, a revision of V4's mHC. First two encoder layers are SWA-only.

## 4. Will it fit this box?

RAM 249 GiB (214 free), VRAM 59.6 GiB across two cards, models on a 14 GB/s NVMe.

Engram is sparse and belongs on disk, so the resident problem is the 286.4 GiB backbone, of which 269 GiB is
experts. **That exceeds available RAM by roughly 55 GiB.** The engine today pins every expert in host RAM and
*hard-refuses* a model whose experts have no host copy, so this needs a third tier: experts backed by the NVMe,
faulted on miss. That is a new subsystem, though a natural extension of the existing pinned-arena design and
exactly what the 9100 PRO is for.

Rough decode estimate once running: 240 expert activations per token x ~16.9 MiB = ~4.2 GiB at zero cache hit;
at a plausible 0.6 VRAM hit rate, ~1.7 GiB per token moving, mostly RAM→VRAM over PCIe at 26.5 GB/s with ~20% off
the NVMe. That lands near **10–15 tok/s**. An estimate from component bandwidths, not a measurement.

## 5. What has to be built

Free (reuse as-is): routed-expert kernels, the MXFP4 bank and cache machinery, the pinned host arena, two-card
expert tensor-parallelism, the mHC tensor contract, sampling, the server.

Contained (bounded, host-testable):
1. **safetensors reader** — the engine loads GGUF only; 48 shards, 96k tensors.
2. **FP8 E4M3 + block-scale dequant** at load for the ~7 GiB of dense weights, the same shape of change as the
   Q8_0 work committed this morning.
3. **Config/arch registration** for `deepseek_v41` and its layer-kind table.

Genuinely new and large, roughly in dependency order:
4. **CED forward structure** (encoder/decoder split, decoder KV projected from `H_{L/2}`).
5. **CSA2** three-mode attention with cross-layer KV and index sharing.
6. **Hierarchical Sparse Indexer** and the shared candidate pool.
7. **NVMe-backed expert tier** (the ~55 GiB that will not pin).
8. **Engram** lookup subsystem, memory-mapped.
9. **FP4 KV cache.**
10. **DeepSeek-ViT** vision tower (2D-RoPE, linear patch embed, 3x3 pixel-unshuffle) and the aligner.
11. **DSpark** speculative decoding — last, it is an optimisation.

## 6. Honest assessment

This is **weeks of work, not days**, and items 4–6 are the ones that could go badly: they rewrite the attention
path rather than extend it. The first honest milestone is *"loads, and one layer's output matches the reference
implementation"*, not *"serves"*.

Two things make it more tractable than it looked this morning: the expert bulk is already in a format the engine
runs, and there is a complete reference implementation to check every stage against. Two things make it harder
than the GLM-5.3 port: that model arrived as GGUF and fitted in RAM; this one does neither.

The cheapest next step, and the one that de-risks everything downstream, is a standalone loader that reads the
safetensors, dequantises one dense tensor and binds one expert, and checks both against the reference — no GPU, no
engine changes.
