# V4.1 port — Phase 4 result (2026-09-12)

**Verdict: criteria met, with criterion 2 falsified and replaced.** First GPU work in this port.
`ie-ds41-device-test`: 384 experts uploaded and verified. Wall time is page-cache dependent
(8.00 s cold here, 3.61 s warm on the gate's run) and is not a claim about anything.

## The finding: the expert layouts are NOT identical

`00_PORT_SCOPE` opened with the claim that made this port look cheap — V4.1's routed experts are
already MXFP4, so the 269 GiB that would have dominated the work "bind straight onto kernels
this engine already has". Phases 2 and 3 supported it at every level they could see: the 16-code
nibble table is bit-identical to the engine's `0xC8643210`, the planes are `[N, K/2]` and
`[N, K/32]` exactly as `DS4ExpertBank` documents, and the byte counts match to the byte.

**All of that is true and the conclusion was still wrong.** Inside each 32-element block:

| | element j (j<16) | element j+16 |
|---|---|---|
| engine (`gemv_mxfp4_soa_f16`, gpt-oss layout) | low nibble of byte **j** | high nibble of byte **j** |
| V4.1 (OCP MX, packed along K) | — | — |
| V4.1: element 2b / 2b+1 | low / high nibble of byte **b** | |

Only elements **0 and 31** land in the same place. Feeding the shipped bytes to the engine's
kernel returns a *permutation* of the correct weights — every value present, every magnitude
plausible, no NaN, no overflow, no assertion. A model built on it would have generated fluent
and confidently wrong text with nothing anywhere to flag it.

### What caught it

Criterion 3: run the existing `ds4_expert_gemv` with a **one-hot** activation `x = e_{k0}`, so
the sum is a single term and `y[n]` must equal `fp16(W[n,k0])` **exactly**. Results before the
fix:

```
[FAIL] k0=0    (even)  120 of 2304 differ   <- only sign-of-zero
[FAIL] k0=1    (odd)  2086 of 2304 differ
[FAIL] k0=37   (odd)  2097 of 2304 differ
[FAIL] k0=5119 (odd)   125 of 2304 differ   <- only sign-of-zero
```

5119 ≡ 31 (mod 32). The two indices that agreed are exactly the permutation's fixed points,
derived independently on paper afterwards — so the failure pattern identified the defect
precisely rather than merely signalling one.

**No byte-comparison, shape check, dtype census, or dequantisation test could have found this.**
It needed arithmetic that distinguishes *which* weight is at *which* index, which is what a
one-hot probe is for.

### The fix

A pure 16-byte shuffle at upload, one work-item per block holding all 16 bytes in registers so
it runs in place with no second buffer and no race:

```
engine_byte[j] = nib(v41[j/2], j&1) | (nib(v41[j/2 + 8], j&1) << 4)
```

The original conclusion survives in weakened form: **no new expert kernel, no requantisation,
no dequantisation** — every existing tuned MXFP4 kernel runs unmodified after the shuffle. The
cost is one pass over each plane at upload, which is free next to the read that delivers it.

## Two smaller notes

- **Criterion 5 was amended *before* building**, and the amendment is the interesting half: the
  original said to run the fp16 dequant with an E8M0 scale of 0 (2^-127) and check for non-zero
  output. That test cannot work — 2^-127 x 448 is ~2^-118 and fp16's smallest subnormal is
  2^-24, so every correct implementation returns zero. It would have "passed" while testing
  nothing. Replaced by a direct device-vs-host comparison of both decoders over all 256 codes at
  fp32, which does execute the subnormal path on device. It passes, so icpx's fast float model
  does not flush it there — but only because the value is built from bits rather than arithmetic.
- **Zeros in criterion 3 compare by value, not bit pattern.** The GEMV accumulates into a `+0.0`
  register and `0.0 + (-0.0) == +0.0` in IEEE, so a weight of `-0.0` arrives as `+0.0`
  legitimately. Every non-zero still matches bit for bit.

## Where this leaves the port

The two device primitives the forward pass needs now exist and are verified: experts land
correctly and dense FP8 dequantises correctly. Next is the residency planner (which experts live
in VRAM, which in host RAM, which stream from NVMe) and then the forward pass itself.

## Gate verdict: FAIL, then fixed (2026-09-12)

The Phase 4 gate returned **FAIL** on two criteria this document had reported as met. Both
findings were correct and both are now fixed; the engineering and the nibble-order finding were
confirmed, including an independent verification of the permutation in both directions.

**Criterion 6 was a tautology.** The check was `bank_bytes == need`, and both sides were built
from the same expression (`E * N * K/2 + E * N * K/32`). It could not fail — it restated the
implementation rather than measuring anything. It also covered only the `w1` bank, 2.24 GiB,
while the criterion had named a whole layer at 6.72 GiB.

It now compares two genuinely independent quantities: the bytes the **checkpoint itself
declares** for these tensors (summed from the safetensors headers) against the VRAM the
**driver reports consumed** (`ext_intel_free_memory` before and after), over all three banks.
Result: 6.724 GiB declared, 6.7923 GiB consumed, **17.93 MiB per expert** — the figure the
criterion actually named.

**Criterion 7 did not exist in the test.** The result table claimed "all device allocations
freed", which is weaker than the criterion (free VRAM before/after) and was not measured at all,
even though the B70 supports `ext_intel_free_memory`. The test now reports it and requires the
memory back: 31.861 GiB → 31.792 GiB, 70 MiB unreturned (runtime/kernel cache, not the 6.7 GiB).

**The root cause under both**, worth stating because it generalises: I wrote checks that
*restate the implementation* instead of measuring an independent quantity. A check whose two
sides come from the same expression is decoration. The rule this phase adds — a check must
compare something the code computes against something it does not.

## Second gate pass: two more findings, both fixed (2026-09-12)

The gate's full report carried two further blocking findings beyond the tautology and the
missing free-VRAM check.

**The falsified claim survived in the header of the function that falsified it.**
`deepseek41_upload.hpp` still told the reader "this is a copy, not a repack — the engine's
existing MXFP4 expert kernels read the shipped bytes unmodified." `dtype.hpp`, the port scope
and the `.cpp` were all corrected; the header was missed. It is the first thing a future phase
reads about that function, and believing it is precisely what produces fluent wrong output.
Corrected.

**Criterion 3's probe set did not cover the permutation, and the gate proved it with a mutant.**
`{0, 1, 37, 5119}` are within-block indices `{0, 1, 5, 31}`. 0 and 31 are the permutation's only
fixed points; 1 and 5 both land in the low half. So the `+8` term — the engine's high nibbles,
logical elements 16..30 — was probed **only** at j=15, where source and destination are the same
byte and the same nibble: an identity. The gate built a repack that corrupts elements 16..30 of
every block while sparing j=15, and it **passed all four probes** while failing 15 of 32 indices.

Enumerated afterwards, the old set touched **4 of the 32 distinct (byte, nibble) source
positions** in a block and missed the high nibble of bytes 0..14 entirely. The test now probes
**every within-block index, in two different blocks** — 64 one-hot GEMVs, covering 32/32
positions, exhaustive by construction rather than by argument. It detects the gate's mutant at
15 of its probes.

**On the regression count.** The gate is right that "20/20 host-only" is not reproducible: this
repo has **no host-only test label**, so any such set is an artefact of whichever grep built it
(mine yields 24 targets, the gate's 27). The count is therefore withdrawn as a claim. What is
reproducible: of the set this build runs, the **only** failure is `deepseek4_residency_test`,
which is not host-only — it opens a SYCL queue — and whose 17 failures were verified pre-existing
in Phase 2 by stashing the diff and re-running on a pristine tree. Excluding it: 23/23 pass.

**Two smaller corrections to this document's precision**, both from the gate:
- Criterion 4 compares **fp16** bit patterns, so it catches a one-ulp fp16 difference, not a
  one-ulp fp32 difference in the decoders. Those are criterion 5's job.
- Criterion 5's "two separate implementations" is fully true for E4M3 (the host builds the value
  by multiplication and uses `std::nanf`; the device builds bit patterns with a subnormal table)
  but only weakly true for E8M0, where the device function is close to a transcription of the
  host one. The criterion survives on the absolute anchor instead — `got[256+0] == 0x00400000`
  is 2^-127 checked against a constant, which cannot pass vacuously.
