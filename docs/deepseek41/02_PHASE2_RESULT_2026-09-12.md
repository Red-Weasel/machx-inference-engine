### On criterion 4/5 being *exact*

FP8 E4M3 → fp32 and E8M0 → fp32 are both exact conversions, and the dequant is one fp32
multiply. So is the FP4 path. There is no rounding anywhere, which is why the bar was set at
0.0 rather than a tolerance: any nonzero diff would have been a bug, and a tolerance would have
hidden it. Both came back at exactly 0.0.

The FP4 reference is the OCP MX spec's field layout decoded from first principles, **not**
torch — torch has `float4_e2m1fn_x2` as a dtype but no CPU kernel to unpack it
(`NotImplementedError: "copy_kernel" not implemented for 'Float4_e2m1fn_x2'`). The spec
decode is independent of both torch and the engine's `0xC8643210` constant, so it is a
stronger reference than torch would have been.

## What Phase 2 does and does not establish

Established, precisely: (a) an **exhaustive** size and byte-accounting audit over all 96,085
tensors — every mapped dtype's `bytes_for` equals its shipped `nbytes`; (b) **numeric**
reproduction of the reference on exactly **two** tensors, one per weight family (40 MiB dense,
11.25 MiB expert). The criteria asked for one of each, so the phase passes — but (a) and (b)
are different claims and an earlier draft of this sentence conflated them into "every byte of
449 GiB", which is not what was measured.

Not established, and not claimed: that any of it runs. No config reader, no binder, no
forward pass, no GPU. The 269 GiB of routed experts binding onto existing MXFP4 kernels is a
*layout* match proven at the byte level — the kernels have not been pointed at these tensors.

## Gate findings and what changed because of them (2026-09-12)

The Phase 2 gate returned **PASS with 8 non-blocking findings**. Three were corrections to this
document's own claims and are applied above. Two led to code:

**Coverage of criterion 4 was narrower than its wording.** `layers.0.attn.wq_b.weight` contains
254 of the 256 E4M3 codes, and the two it lacks are exactly the NaN encodings (`0x7F`/`0xFF`);
its scale plane carries only four distinct E8M0 bytes. So "identical NaN/Inf placement" passed
**vacuously**, and the subnormal branch, negative zero, and both ends of the exponent range
were never reached. Closed by `tests/unit/fp8_decode_test.cpp`, which checks **all 256 codes of
each format against torch goldens as bit patterns** (so −0.0 vs +0.0 is a failure, not a tie).

**That new test immediately found a real bug.** `e8m0_to_f32(0)` — the scale 2^-127 — returned
**0.0** instead of `0x00400000`. The old implementation built it by halving 2^-126, and 2^-127
is subnormal in fp32: **icpx defaults to `-ffp-model=fast`, which flushes denormal results to
zero.** The gate's own independent check of the same function did not reproduce it, because it
compiled at `-O0` with gcc, which keeps denormals. The fix constructs the bit pattern directly
(`include/ie/fp8.hpp`). No shipped tensor uses that scale byte, so nothing measured here was
wrong — but a dense weight whose block scale was 2^-127 would have silently dequantised to
zero. **Standing lesson for this codebase: under icpx's default fast float model, any
arithmetic that can produce a denormal returns zero. Build such values from bits.**

Two more findings were acted on: the probe now writes a freshness `stamp` and
`ds41_probe_ref.py` refuses a dump older than 10 minutes, so a stale dump in a reused directory
cannot be compared silently; and the hash-index size comment in `safetensors.hpp` was corrected
from "~6 MB" to ~11 MB.

**On "19/20 host-only":** the repo has no host-only test label; that set came from a grep over
`tests/CMakeLists.txt` comments, and `deepseek4_residency_test` is **not** host-only — it opens
a SYCL queue. Its 17 failures were verified pre-existing (by stashing this phase's diff and
re-running on the pristine tree) and are environmental: both TP cards resolve to GPU 1 without
`DS4_TP_GPUS="0,1"`, plus a MemAvailable-dependent cap assertion. Excluding it, 19/19 pass.
