## The full-model golden

`tools/ds41_reference/golden_model.py` runs the reference's forward through all 40 layers —
each `Block(L)` built, loaded and run in turn as DeepSeek's own code, engram through the
mmap-backed table, experts touched only when routed to — for a real prompt:

```
prompt: 'The capital of France is Paris. The capital of Germany is' -> 12 tokens
40 layers in 233s
next-token top-5: [(' Berlin', 27.492), ('Berlin', 20.492), (' not', 20.174), (' Ber', 19.754), (' Bonn', 19.231)]
```

**The model says Berlin.** That is the strongest possible statement about the harness: the
six stand-ins, the mmap'd engram, the per-layer weight wiring, the compressor at ratio 2 and
ratio 1, the candidate blocks at layer 20 — all of it composes into a model that knows the
capital of Germany. It dumps every layer's output stream (`m_layer_out_{L}`), the engram
outputs at 1 and 14, the final collapsed stream and the logits: the engine's full forward will
be checked against each of them, layer by layer, and its first token against " Berlin".

Two observations from the run for the layer loop: the stream's absmax grows from ~2 at layer 0
to ~25 through the ratio-1 layers and **468 at layer 39** — fp16 activations will need care at
the last layer (the reference computes in bf16/fp32 there); and a layer takes 3.5-10 s on CPU,
so the golden is cheap to regenerate for other prompts.

## Phase 6 gate: FAIL, then fixed (2026-09-12)

One blocking finding, eleven non-blocking. **Every 6a/6b number reproduced exactly on the gate's
own goldens**; the block was in a Phase 5 fix.

**Blocking — a use-after-free in `ds41_hc_parity_test`.** The self-validation block I added
for the Phase 5 gate ran *after* the `sycl::free` loop and read six freed USM pointers. The
gate measured three consequences: the printed discrimination was nondeterministic
(`3.671e-03/8.162e-01` then `7.928e-01/8.079e-01` twice); the "0.79 / 0.81" I had published
were artifacts of freed memory — the true values are **3.671e-3 / 3.262e-3**; and, decisively,
**the guard inverted** — on the trivial input it was added to reject, the freed arrangement
exited 0 while the correct one exits 1. Fixed by moving the frees last; three consecutive runs
now agree. I published numbers read from freed memory. The lesson is not about `sycl::free`;
it is that a number that changes between runs is not a measurement, and I did not run it twice.

## Re-gate: PASS (2026-09-12)

Every fix verified by re-running the mutant that exposed the original. The use-after-free fix
is confirmed by the decisive check: the trivial-input mutant that used to exit 0 now exits 1
("the input is too trivial for this test to guard anything"), three consecutive real runs
agree at 3.671e-3 / 3.262e-3, and a mutant the gate added — the V4.1 copy at 21 iterations
against the V4 kernel's 20 — is caught at 3.262e-3 against the 1e-5 bar.

The gate pushed the tie proof one step further than asked: comparing the **engine's own**
output against the reference run on the engine's own selection, the 30 tie queries agree to
**8.933e-5 — below the 3.959e-4 fp16 floor** the engine shows on the other 1,506. Given its
selection, the engine's arithmetic on those queries is better than its ordinary floor; the
entire 7.07e-3 against the golden was the selection. `prove_ties.py` now computes exactly that
comparison rather than asserting it in prose, reads the test's *measured* tie error instead of
a hardcoded literal, checks that its three dumps come from the same run, and the engine's
artifacts live under `<golden>/eng/` so an experimental run can never overwrite the reference
set — the three new non-blocking findings. Also recorded: with the absolute band, a score
degradation is excused up to about C3 = 1.1e-3 and caught from about 1.6e-3 — the inherent
window of comparing a discrete top-k, now fixed rather than moving with the defect.
